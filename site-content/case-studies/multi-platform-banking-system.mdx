## Multi-Platform Platform (Fintech)

<p className="text-[var(--muted)]">
  <em>Spring Boot · React · Android · FastAPI KYC · OCR/vision modules</em>
</p>

> **TL;DR** — Designed and implemented a modular platform spanning backend, web, mobile, and a FastAPI KYC service. The reviewed evidence covers service boundaries, check policy, and review states; population-level accuracy and false-rejection outcomes are not published without labeled evaluation evidence.

---

### Context & Role
Solo/lead developer across multiple layers. The implementation separates account flows, KYC case state, and wallet communication through explicit API boundaries.

### Problem
- Keep upload ownership, KYC case state, and component checks explicit across service boundaries
- Keep web and Android clients aligned with the Spring API without moving authorization into the clients
- Represent check thresholds and review outcomes without presenting them as measured population results

---

### Approach & Architecture
- <strong>Domain-oriented Spring Boot</strong> modules (auth, accounts, analytics, kyc, wallet)
- <strong>FastAPI KYC service</strong>: face, liveness, OCR, document-classification checks, and an aggregate policy
- <strong>Spring orchestration</strong>: bounded file reads, persisted check records, and UNDER_REVIEW fallback on service failure
- <strong>Android Wallet</strong>: card reload, QR pay, and bill-pay intent flows through Retrofit interfaces and DTOs
- <strong>React Web</strong> client with role-gated routes, bearer-token requests, and account flows

### Challenges & Trade-offs
- KYC service failure → persist an error check and move the case to UNDER_REVIEW rather than approving it
- Upload integrity → require four distinct owned uploads with the expected document categories
- Model boundary → keep optional ONNX/Tesseract modules distinct from the current simple default factory path

### Results
- Implemented explicit KYC upload, case, check, and status boundaries in the reviewed source
- Implemented APPROVE, UNDER_REVIEW, and REJECT policy branches with reason codes and per-check records
- Accuracy, false-rejection rate, manual-review volume, and production outcomes remain unmeasured in the reviewed evidence
