## BankApp (Android) — Wallet Flows

<p className="text-[var(--muted)]">
  <em>Kotlin · Jetpack Compose · Retrofit · Coroutines · Material 3</em>
</p>

> **TL;DR** — Built wallet features for card reloads, QR payments, and bill-pay. The Retrofit API layer maps failures into repository results while the payment view model exposes bounded processing and terminal states.

---

### Context & Role
Android module focused on wallet flows, with the client communicating through explicit API and PaymentIntent states. External-provider settlement is not treated as verified by this case study.

### Problem
- Payment flows were overly coupled to banking onboarding.
- Asynchronous payment intent states need to remain visible while the client polls for a terminal result.

### Approach & Architecture
- Feature-based packages (screens, view models, DI)  
- Retrofit interfaces with clean DTOs, interceptors, consistent error envelopes  
- Compose UI with unified components (cards, inputs, buttons) and a11y labels  
- PaymentFlowViewModel with bounded exponential polling and explicit creating, processing, succeeded, failed, and canceled states

### Challenges & Trade-offs
- Duplicate payment-intent creation → send an Idempotency-Key from the Android repository
- Long-running requests → poll with backoff capped at ten seconds and a two-minute client timeout
- UI complexity → keep API/repository failures separate from the view-model state machine

### Results
- The client models payment creation, processing, success, failure, cancellation, and timeout as distinct states
- Repository methods expose API/network failures instead of treating unsuccessful responses as completed payments
- External-provider settlement and production payment outcomes remain unverified
